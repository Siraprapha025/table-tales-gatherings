# รับเงินค่าจองโต๊ะด้วยการโอนและตรวจสลิปเอง

ผู้จัดแต่ละรายตั้งบัญชีรับเงินของตนเองในแต่ละงาน เงินโอนเข้าบัญชีนั้นโดยตรง เว็บเก็บการจอง สลิป และผลตรวจ ไม่ถือเงินและไม่ติดต่อธนาคารเพื่อยืนยันยอด

## ติดตั้ง

1. ทำตาม README เพื่อตั้ง Supabase Auth, server environment และ baseline schema
2. รัน migration ที่ยังไม่เคยใช้ตามลำดับ: `20261022110000_booking_safety.sql` แล้ว `20261023090000_manual_payments.sql` บนฐานข้อมูลทดสอบก่อน
3. migration ล่าสุดสร้างคอลัมน์การเงิน ตารางประวัติ RPC และ Storage bucket `payment-proofs` แบบ private จำกัด JPEG/PNG 5 MiB
4. ตั้ง `SUPABASE_SERVICE_ROLE_KEY` ฝั่งเซิร์ฟเวอร์เท่านั้น ห้ามใส่ `VITE_*` หรือ commit และใช้ project เดียวกับค่าฝั่งหน้าเว็บ
5. ถ้าใช้ Supabase เดิมที่มี Storage policies กว้างอยู่แล้ว ให้ตรวจว่าไม่มี policy อื่นเปิดให้ลูกค้าหรือผู้จัดข้ามรายอ่าน bucket นี้ผ่าน Storage โดยตรง
6. ใช้โฮสต์ที่รัน TanStack Start/Nitro server ได้ ตั้ง Auth redirect URL และ HTTPS ให้ตรงโดเมนจริง และให้ reverse proxy เขียนทับ IP headers ก่อนส่งเข้าแอป

การ build, test และ Push โค้ดไม่รัน migration ไม่ตั้ง secrets และไม่เผยแพร่เว็บไซต์ให้อัตโนมัติ

## วิธีใช้

ผู้จัดสร้างงาน → เลือกโอนเงินต่อโต๊ะ → กรอกธนาคาร/ชื่อบัญชี/เลขบัญชี → ตั้งมัดจำ 1–100% และเวลาชำระมัดจำ → ตั้งวันชำระส่วนที่เหลือระหว่างปิดรับจองกับเริ่มงาน → ระบุเงื่อนไขยกเลิก/คืนเงิน → ตั้งราคาแต่ละโต๊ะ → เผยแพร่และแชร์ลิงก์

ลูกค้าเลือกโต๊ะ → ตรวจราคารวม มัดจำ วันครบกำหนด และเงื่อนไข → ยืนยันจอง → เก็บลิงก์ส่วนตัว → เปิดหน้าการจองดูบัญชีรับเงิน → โอนและแจ้งยอดจริง/เวลา/แนบสลิป

ผู้จัดเปิดแท็บ **รับเงิน / คืนเงิน** → ดาวน์โหลดสลิป → ตรวจรายการเงินเข้าจากบัญชีธนาคาร → ใส่เลขอ้างอิงของรายการเงินเข้าที่ไม่ซ้ำ → ยืนยัน หรือปฏิเสธพร้อมเหตุผล หากอนุมัติผิด ระบบยังไม่มีคำสั่งกลับรายการเงินรับ ต้องให้ผู้ดูแลตรวจและแก้ด้วยกระบวนการที่เก็บ audit ก่อนเปิดใช้งานจริง

เมื่อรับมัดจำครบ การจองเปลี่ยนเป็นยืนยันแล้ว แต่ยังแสดงยอดส่วนที่เหลือ ลูกค้าแจ้งโอนส่วนที่เหลือด้วยวิธีเดิม รายงานนับเฉพาะรายการที่ผู้จัดยืนยันแล้ว

## กฎการเงิน

- หน่วย API/ฐานข้อมูลคือสตางค์ เช่น 1,000 บาท = 100000; ยอดรวมต่อการจองไม่เกิน 1,000,000 บาท
- คิดตามราคาโต๊ะที่เลือก มัดจำปัดขึ้นเป็นสตางค์ วันครบกำหนดมัดจำไม่เกินกำหนดชำระส่วนที่เหลือ
- เก็บสำเนาราคา บัญชีรับเงิน มัดจำ กำหนดชำระ และเงื่อนไขไว้กับการจอง การแก้งานภายหลังไม่เปลี่ยนข้อมูลของผู้จองเดิม
- ตรวจราคารวมและ version งานอีกครั้งก่อนจอง ถ้าเปลี่ยนให้ลูกค้าตรวจและยืนยันใหม่
- สลิปรอตรวจไม่ใช่ยอดเงินรับ การส่งซ้ำด้วย request_id และข้อมูลเดิมคืนรายการเดิม; เปลี่ยนข้อมูลใช้ request_id ใหม่
- ตรวจ hash ของไฟล์ซ้ำและเลขอ้างอิงธนาคารซ้ำภายในผู้จัดรายเดียวกัน ไม่ใช่ระบบตรวจสลิปปลอมหรือ OCR
- เกินกำหนดชำระ **ยังไม่ปล่อยโต๊ะอัตโนมัติ** ผู้จัดตรวจบัญชีก่อนยกเลิกด้วยเหตุผลในแท็บรับเงิน หากยังมีสลิปรอตรวจต้องตัดสินรายการเหล่านั้นก่อน
- ยกเลิกแล้วจึงบันทึกคืนเงินได้ ผู้จัดต้องโอนคืนเองก่อนกรอกยอด เวลา เลขอ้างอิง และหมายเหตุ ระบบกันยอดคืนเกินเงินรับและบันทึกซ้ำ
- คืนบางส่วนได้ตามเงื่อนไข ยอดที่ยังไม่คืนไม่ถูกนับเป็นยอดคืนแล้ว สถานะ `refund_pending` จะคงอยู่จนคืนครบยอดที่รับ รุ่นนี้ยังไม่มีสถานะปิดเรื่องแบบไม่คืน/หักค่าธรรมเนียม
- CSV แสดงราคารวม รับแล้ว คืนแล้ว และค้างชำระของการจองที่ยังใช้งาน พร้อมป้องกันข้อความลูกค้าเป็นสูตร spreadsheet

## API ที่เพิ่ม (8 รายการ รวม API ทั้งหมด 23 method/path)

ทุก path มี prefix `/api/v1`.

| Method | Path                             | สิทธิ์ / ข้อมูล                                                                      |
| ------ | -------------------------------- | ------------------------------------------------------------------------------------ |
| GET    | `/booking/payments`              | X-Manage-Token; ยอด บัญชีสำเนา เงื่อนไข ประวัติของตน                                 |
| POST   | `/booking/payments`              | X-Manage-Token; multipart: file, amount_satang, paid_at (ISO UTC), request_id (UUID) |
| GET    | `/booking/payments/{id}/proof`   | X-Manage-Token; ดาวน์โหลดสลิปของการจองนั้น                                           |
| GET    | `/manager/events/{id}/payments`  | Bearer; สลิปและคืนเงินของงานที่ตนเป็นเจ้าของ                                         |
| GET    | `/manager/payments/{id}/proof`   | Bearer; ดาวน์โหลดสลิปในงานของตน                                                      |
| POST   | `/manager/payments/{id}/review`  | Bearer; `{approve,reference,note}`                                                   |
| POST   | `/manager/bookings/{id}/refunds` | Bearer; `{amount_satang,paid_at,reference,note,request_id}`                          |
| POST   | `/manager/bookings/{id}/cancel`  | Bearer; `{note}`                                                                     |

ดู JSON schemas ใน `public/openapi.json`. หน้าทดสอบ API ส่ง JSON ได้ ส่วนอัปโหลดและดาวน์โหลดไฟล์ให้ใช้หน้าจอง/หน้ารับเงิน หรือ client ที่รองรับ multipart/binary

มีบริการภายนอกที่ต้องตั้งค่าตอนนี้คือ **Supabase** ใช้ Auth + PostgreSQL/RPC + Storage ส่วน API ของแอปอยู่บนเว็บเซิร์ฟเวอร์เดียวกัน ไม่ต้องซื้อ payment gateway หรือ API ธนาคารสำหรับขั้นตอนโอนด้วยตนเองนี้ LINE และ AI ยังไม่ได้เชื่อมต่อ

## ทดสอบก่อนรับลูกค้าจริง

ทดสอบด้วยผู้จัดสองบัญชีและลูกค้าคนละ browser บน staging: จองโต๊ะเดียวกันพร้อมกัน, จองงานฟรี/เก็บเงิน, ส่งสลิปซ้ำ, อนุมัติมัดจำ, ชำระส่วนที่เหลือ, ปฏิเสธสลิป, ยกเลิกหลังรับเงิน, คืนบางส่วน/ครบ, ส่งคำขอซ้ำขณะเครือข่ายขัดข้อง และยืนยันว่าอีกผู้จัด/อีก token ดาวน์โหลดสลิปไม่ได้

การทดสอบอัตโนมัติใช้ PGlite และ React test environment ไม่ได้ทดสอบ Supabase Storage จริง ธนาคารจริง หรือ lock contention หลาย connection ต้องทดสอบครบ workflow บนโฮสต์เป้าหมายก่อนเปิดรับเงินจริง

ตั้งการสำรองข้อมูลและระยะเวลาเก็บ/ลบสลิปให้เหมาะกับการใช้งาน ไฟล์ที่อัปโหลดสำเร็จแต่บันทึกฐานข้อมูลล้มเหลวอาจค้างเป็น orphan โดยตั้งใจไม่ลบเมื่อไม่แน่ใจว่าธุรกรรมสำเร็จหรือไม่ การล้างไฟล์ต้องเทียบ `proof_path` กับฐานข้อมูลและเว้นช่วงเผื่อรายการกำลังส่ง ไม่มีงานล้างอัตโนมัติในรุ่นนี้

แนวทาง Storage: [Private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals) และ [Downloads](https://supabase.com/docs/guides/storage/serving/downloads). แอปนี้ส่งไฟล์ผ่าน API ที่ตรวจสิทธิ์ทุกครั้ง ไม่คืน public URL ให้ลูกค้า
